## 1. Project Architecture
- **Goal:** Automate Sales, Purchase, and Bank entries directly into **Miracle Accounting Software** by injecting records into its underlying FoxPro (`.DBF`) database files.
- **Backend:** Python (FastAPI). Uses the `dbf` library to read/write FoxPro databases. The core logic is heavily concentrated in `backend/dbf_handler.py`.
- **Frontend:** React / Next.js.
- **Workflow:** The user uploads Excel/CSV data -> Backend parses it -> Backend maps names to Ledger Codes -> Backend injects transactions into Miracle's active year folder (e.g., `YR26`).

## 2. Miracle Database Mappings (Crucial)
Miracle uses heavily inter-linked tables. Injecting a voucher requires updating multiple tables synchronously:
- **`RKACCM01.DBF` & `RKACCM02.DBF`:** Party Ledgers and Account details.
- **`RKACCM14.DBF`:** HSN / Commodity Masters.
- **`RKACCM21.DBF`:** Product Master.
- **`RKACCT41.DBF`:** Transaction Header (Summary of the voucher, total amount, party code).
- **`RKACCT02.DBF`:** Transaction Details (Breakdown of individual items, qty, rate, product links).
- **`RKACCT52.DBF`:** GST / Tax Ledger Breakdown. Links the transaction to GSTR reports. **If this is wrong, entries don't show up in GST books or they appear red!**

## 3. Bug History & Solutions (Do NOT Repeat These Mistakes)

### Bug 1: The "Red Text" & Missing GST Book Bug for Purchases
**Symptom:** Purchase entries injected via our tool showed up in the Miracle grid with **Red Text**. When clicking them, Miracle behaved unpredictably or failed to edit. Furthermore, the entries did NOT show up in the GST Purchase Ledgers. (Sales worked perfectly, however).
**Effort to Solve:** This took roughly **10 intense debugging conversation turns** and deep-dive comparisons between "Manual entries" (created inside Miracle UI) and "Injected entries" (created by our Python script).
**Root Cause found:** We were writing "Sales" database flags for *everything*. Miracle uses very specific single-character string flags to differentiate Sales vs. Purchases. 
**The Solution (Implemented in `dbf_handler.py`):**
When injecting `RKACCT02` (Line Items):
- `FIELD04`: Must be `'N'` for Purchases, `'I'` for Sales.
- `FIELD05`: Must be `'C'` for Purchases, `'D'` for Sales.

When injecting `RKACCT52` (GST/Tax Summary):
- `T52F05`: Must be `'C'` for Purchases, `'T'` for Sales.
- `T52F22`: Must be `'C'` (Credit) for Purchases, `'D'` (Debit) for Sales.
- `T52F28`: Must be `'C'` for Purchases, `'T'` for Sales.
- `T52F29`: `'O'` for both.
- `T52F30`: Must be `'4'` (Purchase Book) for Purchases, `'3'` (Sales Book) for Sales.

### Bug 2: Missing Party Ledgers causing crashes
**Symptom:** Trying to link a voucher to a non-existent Party Code.
**Solution:** `dbf_handler.py` implements an auto-creation function (`create_party_ledger`) that auto-registers missing B2B/B2C parties into `RKACCM01` and `RKACCM02`, and auto-generates a GUID in `RKACCGID.DBF`.

## 4. How to Debug Miracle DBF Issues
If a new issue arises where Miracle UI rejects our entries:
1. **Never guess the DBF flags.** Miracle's schema is undocumented. 
2. **Create a manual entry** inside the Miracle Software UI that represents exactly what you want to achieve.
3. Write a Python script to **read and print that manual record** from the relevant `.DBF` files (`RKACCT41`, `RKACCT02`, `RKACCT52`). 
4. Compare every single field between the manual record and our Python-injected record. Find the discrepancy.
